> Рішення CEO, ухвалені на брейнштормі:

Дизайнер (і будь-хто інший) має бачити всю історію справи й писати по ній, **не покидаючи поточного екрана** — з канбану, зі списку, зі сторінки задачі. Сьогодні коментарі є, але щоб їх побачити, треба відкрити сторінку і дошкролити.

## 3. Архітектура фази A

**Глобальна шторка**, змонтована один раз в `AppLayout`, керована маленьким стором: `openThread({ anchor })` з будь-якої точки CRM. Відкидаємо: вбудовану колонку (не викликається з канбану, ламає верстку великих сторінок) і плаваючий док у стилі Intercom (власний менеджер вікон, конфлікт із діалогами).

**Ключ нитки** — `thread_key text`:

| Звідки відкрили | `thread_key` |
|---|---|
| Прорахунок | `quote:<quote_id>` |
| Дизайн-задача | `quote:<metadata.quote_id>` |
| Замовлення з прорахунку | `quote:<order.quote_id>` |
| Ручне замовлення (без прорахунку) | `order:<order_id>` |

Наслідок і є суттю рішення №2: прорахунок, його дизайн-задача і його замовлення відкривають **одну й ту саму нитку**. Ручні замовлення (де `quote_id is null`, див. `project_manual_order_creation`) отримують власну — інакше вони не мали б до чого чіплятись.

## 4. Зміни в БД

Розширюємо наявну `tosho.quote_comments`, а не заводимо нову таблицю: обидві сторінки вже з неї читають, наявний код не ламається, міграція мінімальна.

```sql
alter table tosho.quote_comments
  add column if not exists thread_key  text,
  add column if not exists kind        text not null default 'message',  -- 'message' | 'event'
  add column if not exists visibility  text not null default 'team',     -- 'team' | 'internal'
  add column if not exists source      text not null default 'crm',      -- 'crm' | 'telegram' (наперед, фаза C)
  add column if not exists event_type  text,                             -- лише для kind='event'
  add column if not exists is_pinned   boolean not null default false,   -- закріплене ТЗ угорі стрічки
  add column if not exists metadata    jsonb not null default '{}'::jsonb;

update tosho.quote_comments set thread_key = 'quote:' || quote_id where thread_key is null;

alter table tosho.quote_comments
  alter column thread_key set not null,
  alter column quote_id   drop not null,   -- ручні замовлення без прорахунку
  alter column created_by drop not null;   -- системні події не мають автора

create index if not exists quote_comments_thread_idx
  on tosho.quote_comments (thread_key, created_at desc);
```

Повідомлення й події — **одна таблиця**: стрічка виходить одним запитом із коректною пагінацією, без злиття двох джерел на клієнті.

`created_by` навмисно робимо nullable. Це прямий урок із `quote-status-audit-trigger` (`project_quote_status_audit`): там тригер тихо ламався саме об `NOT NULL changed_by`, коли запис ішов не від імені користувача.

Позначки прочитаності — окрема маленька таблиця:

```sql
create table if not exists tosho.thread_reads (
  user_id      uuid not null references auth.users(id) on delete cascade,
  thread_key   text not null,
  last_read_at timestamptz not null default now(),
  primary key (user_id, thread_key)
);
```

## 5. Звідки беруться події

Тригер `after update on public.activity_log` для рядків `action = 'design_task'`: порівнює `old.metadata` з `new.metadata` за білим списком ключів (статус, виконавець, дедлайн, кількість правок) і дописує в нитку рядок `kind = 'event'`. Автор — `auth.uid()`, який може бути `null` (запис із Netlify-функції service-role-ключем).

Чому в БД, а не з фронтенду: у `DesignTaskPage` понад тридцять місць пишуть в `activity_log`, і частина подій приходить із Netlify-функцій. Обходити всі виклики — гарантовано щось пропустити; тригер ловить будь-який шлях запису. Ціна відомa: тригер живе в `scripts/*.sql`, і його правки не покриті `tsc`/`lint`.

Статуси прорахунку вже мають власну історію (`quote_status_history` + тригер) — на фазі A їх у стрічку **не тягнемо**, щоб не подвоювати джерела. Розглянемо після того, як стрічка подій дизайну попрацює.

## 6. Realtime

Підписка на `tosho.quote_comments` з фільтром `thread_key=eq.<key>`, поруч із наявними каналами в `AppLayout`, з повагою до `realtimeDisabled`.

**Граблі, які інакше з'їдять пів дня:** наявні підписки дивляться на схему `public`, а `quote_comments` живе в `tosho`. Таблицю треба окремим рядком міграції додати в публікацію — інакше підписка не працює **мовчки**, без жодної помилки:

```sql
alter publication supabase_realtime add table tosho.quote_comments;
```

## 7. Доступи

- `visibility = 'team'` — усі, хто вже мав доступ до рядків нитки (чинна політика за `team_id` лишається).
- `visibility = 'internal'` — додатково `tosho.has_finance_access(team_id)`. Нового поняття прав не вводимо.
- Прапорець «внутрішня» в композері **показуємо лише тим**, хто проходить цей гейт, — інакше людина пише нотатку, якої потім сама не бачить.
- Заборона на рівні БД, не UI: політика `select` перевіряє `visibility = 'team' or tosho.has_finance_access(team_id)`.
- Пам'ятка: owner бачить усе за задумом (`feedback_owner_sees_everything`) — це не витік.

## 8. Шапка: чия це справа

Справи в нас розрізняються не номером, а брендом замовника — тому шапка починається з нього, а не з назви задачі.

- Логотип — **канонічний `EntityAvatar`** ([src/components/app/avatar-kit.tsx:393](../src/components/app/avatar-kit.tsx)): є `logo_url` — показує його, немає або не завантажився — кольорові ініціали за тоном назви. Власного `<img>` не пишемо (`feedback_avatars_canonical`).
- Дані вже під рукою: `customer_logo_url` вантажиться в списках прорахунків ([src/lib/toshoApi.ts:399](../src/lib/toshoApi.ts), `optionalColumns`), а `normalizeCustomerLogoUrl` нормалізує посилання.
- **Лід і замовник — різні сутності**, і плутати їх не можна: лід позначаємо бурштиновим чипом «Лід». `partyHoverInfo.ts` уже вміє обидва види й лениво довантажує контакти під курсором — переюзовуємо для картки під наведенням, нічого не пишемо з нуля.
- **Смужка стадій** — Прорахунок · Дизайн · Замовлення, з поточною підсвіченою; клік веде на відповідну сторінку. Вона ж пояснює користувачу, чому в одній нитці лежить листування з трьох екранів. Для ручного замовлення показуємо один сегмент — смужка не вигадує етапів, яких не було.
- Дедлайн у шапці стає бурштиновим, коли лишилось менше трьох днів.

## 9. Стани UI (перелік для макетів)

Порожня нитка; завантаження скелетом; своє й чуже повідомлення; групування підряд від одного автора; роздільник дати; роздільник «нові»; кнопка «N нових» при прогортуванні вгору; закріплене ТЗ; внутрішня нотатка; згадка на тебе; системна подія; посилання на вкладення; довге повідомлення згорнуте до трьох рядків; мітка «прочитали»; помилка надсилання з повтором; композер у трьох станах (звичайний, диктовка, автокомпліт згадки) плюс режим «внутрішня»; шапка для замовника з логотипом, замовника без логотипа, ліда й ручного замовлення; бейдж непрочитаного на картці канбану; мобільний вигляд; нитка недоступна за правами. Фаза C додає бейдж джерела «з Telegram».

**Закріплене ТЗ** — колонка `is_pinned boolean not null default false` у тій самій таблиці; у шапці стрічки показуємо останнє закріплене. Найчастіше питання дизайнера — «а що там просили?» — має отримати відповідь без гортання.

**Мітка «прочитали»** нової таблиці не потребує: це кількість рядків `thread_reads`, де `last_read_at >= created_at` повідомлення.

## 10. Поведінка, яку легко проґавити в коді

- **Докручуємо лише знизу.** Нове повідомлення зсуває стрічку тільки якщо користувач уже внизу; інакше показуємо кнопку «N нових», а позиція не рухається.
- **Надсилання оптимістичне**: повідомлення з'являється миттєво блідим; помилка не ковтає текст, а лишає його з кнопкою «Повторити».
- **Панель — це діалог**: `role="dialog"`, фокус переходить усередину при відкритті, Esc закриває, фокус повертається на кнопку-джерело.
- **Прочитано — при закритті або через ~3 с перегляду**, а не в мить відкриття: інакше «заглянув на секунду» гасить лічильник брехливо.
- **Колір ніколи не єдиний носій сенсу**: внутрішня нотатка має тло, замок і підпис; правка — крапку і слово.
- **Іконки — Lucide** (уже в залежностях), не емодзі: емодзі різні на кожній ОС і не фарбуються під тему.
- **Дотик**: на телефоні керування не менше 36–44 px.
- Анімацію шторки вимикає `prefers-reduced-motion`.

## 12. Ризики й відкриті питання

- **Історія не відновлюється.** Стрічка подій починається з дня впровадження — старі зміни статусів втрачені назавжди.
- **Тригер поза типами.** Помилка в `plpgsql` не ловиться `tsc`/`lint`; потрібна ручна перевірка на проді після застосування SQL.
- **`quote_comments` переростає ім'я.** Після фази A таблиця вже не «коментарі прорахунку». Перейменування тягне за собою Netlify-функцію `quote-comments` і два великі файли — свідомо відкладаємо, не робимо «заодно».
- **Видалення з Telegram** (фаза C) вебхук не бачить — дзеркало буде append-only. Редагування синхронізуються.
- **Ліміт Bot API 20 МБ** (фаза D): скріни проходять, важкі сорси лишаються через CRM/Dropbox.
- **Відкрите питання фази B:** модель груп (одна спільна з топіками чи по відділах) навмисно не вирішена — вирішуємо після фази A.

## 13. Перевірка

`npx tsc --noEmit` + `npm run lint` на фронтенді. SQL застосовується через `psql` із `BACKUP_DB_URL` (див. `reference_apply_prod_sql`), окремим кроком, з перевіркою: тригер спрацював на тестовій зміні статусу, підписка realtime приносить нове повідомлення, «внутрішня» нотатка не видно з-під акаунта без доступу до Фінансів.
