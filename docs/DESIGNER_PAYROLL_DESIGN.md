## 1. Модель компенсації

**Зарплата = фіксована база + змінна частина.** Всі суми до оподаткування.

```
нормо_дні = робочі_дні(пн–пт, UA-календар) − дні відпустки/лікарняного

Зароблено(сьогодні) =
    базова_ставка × (робочі_дні_що_минули / робочі_дні_місяця)     // БЕЗ вирахування відсутностей
  + max(0, візуалів − 7 × нормо_дні_що_минули) × 100 грн
  + max(0, макетів  − 4 × нормо_дні_що_минули) × 200 грн
  + Σ (вартість_платного_креативу × відсоток_дизайнера)            // лише статус «Затверджено»
```

- **База** — індивідуальна місячна ставка (напр. 40 000 грн), виставляє
  SEO/owner. Накопичується пропорційно робочим дням. **Відсутності базу не
  зменшують** — за день лікарняного ставка нараховується повністю.
- **Норма — денна, не місячна (рішення CEO 2026-07-26).** У місяці буває 21–23
  робочі дні (травень 2026 — 21, липень — 23): місячна норма карала за короткі
  місяці. Денна множиться на **нормо-дні** = робочі дні мінус відпустка й
  лікарняний, тож за день відсутності норму не набирають. Асиметрія «база не
  ріжеться, норма ріжеться» — свідома, на користь людини.
  - **візуали: 7/день, 100 грн за кожен понад норму;**
  - **макети: 4/день, 200 грн за кожен понад норму.**
  - Норма рахується «на сьогодні» (× нормо-дні, що минули), тому доплата видна
    протягом місяця, а не стрибає в останній день. Побічний ефект: якщо
    дизайнер вирвався вперед і пригальмував, сума у віджеті може зменшитись —
    це чесний live-розрахунок.
- **Що рахується як одиниця:** **унікальна робота**, а не файл — `(задача +
  базова назва без розширення)`. Підстава — дані: один візуал перезаливають
  після правок по 5–9 разів (`tosho_візуал_для_бінфілд-04`: 9 завантажень,
  9 storage_path, 6 різних днів, усі `.png`). Рахунок «за файл» оплачував би
  одну роботу 9 разів і робив би правки вигідними. Правки покриті базою.
  Вид беремо з події завантаження: `output_kind='visualization'` — візуал,
  усе інше — макет.
- **Платні креативи** — див. нижче; вони поверх норми й у неї не входять.
- **Платні креативи** — задача типу `creative` може бути платною (мін. 4 500 грн
  для клієнта). Дизайнер отримує 30% від вартості проєкту **в момент переведення
  задачі в «Затверджено»**. Відкат статусу → нарахування зникає (розрахунок
  завжди live від поточного стану — окремого «сторно» не треба). Безкоштовні
  креативи йдуть у норму візуалів, грошей не дають.

### Симуляція на реальних даних (квітень–липень 2026)

**Разом 14 300 ₴ за 4 місяці на двох** (≈ 45 000 ₴/рік). До бази Лєни це
+7% у середньому, +14% у найкращий місяць. **70% доплати дають макети** —

|---|---|---|
| 9 / 5 на день | 0 ₴ | 1 200 ₴ |

10/5 (перша пропозиція) дає 1 200 ₴ на двох за 4 місяці: 10 візуалів/день —
вище за історичний максимум (8.3 у Лєни в червні).

## 3. Схема даних (все в `tosho`, нові таблиці)

```sql
-- Індивідуальні тарифи. Історія — рядками: чинний тариф на місяць M =
-- рядок з максимальним effective_from <= першого числа M.
-- Зміна ставки завжди набирає чинності з 1 числа наступного місяця (UI не дає інших дат).
create table tosho.employee_pay_rates (
  id                  uuid primary key default gen_random_uuid(),
  workspace_id        uuid not null,
  user_id             uuid not null,
  base_month_rate     numeric(12,2) not null,        -- грн/міс
  visual_norm_per_day int,                            -- override дефолту (null = дефолт)
  layout_norm_per_day int,
  visual_over_rate    numeric(12,2),                  -- грн за візуал понад норму
  layout_over_rate    numeric(12,2),                  -- грн за макет понад норму
  creative_percent    numeric(5,2),                   -- % дизайнера з платного креативу
  effective_from      date not null,                  -- завжди 1 число місяця
  created_by          uuid not null,
  created_at          timestamptz not null default now(),
  unique (workspace_id, user_id, effective_from)
);

-- Дефолти команди (один рядок на workspace).
create table tosho.employee_pay_defaults (
  workspace_id        uuid primary key,
  visual_norm_per_day int not null default 7,
  layout_norm_per_day int not null default 4,
  visual_over_rate    numeric(12,2) not null default 100,
  layout_over_rate    numeric(12,2) not null default 200,
  creative_percent    numeric(5,2) not null default 30,
  min_creative_cost   numeric(12,2) not null default 4500,
  updated_by          uuid, updated_at timestamptz
);

-- Закриття місяця: знімок сум, далі не перераховується заднім числом.
create table tosho.employee_pay_month_close (
  workspace_id uuid not null,
  user_id      uuid not null,
  month        date not null,                         -- 1 число
  base_uah     numeric(12,2) not null,
  over_norm_uah numeric(12,2) not null,               -- разом за обидва види
  visual_over_uah numeric(12,2) not null,             -- з них за візуали
  layout_over_uah numeric(12,2) not null,             -- з них за макети
  creatives_uah numeric(12,2) not null,
  total_uah    numeric(12,2) not null,
  details      jsonb not null,                        -- розбивка: списки креативів, лічильники
  closed_by    uuid not null, closed_at timestamptz not null default now(),
  primary key (workspace_id, user_id, month)
);

-- Винятки робочого календаря (свята/перенесення). Порожня на старті:
-- під час воєнного стану державні свята не є вихідними.
create table tosho.ua_workday_exceptions (
  workspace_id uuid not null,
  day          date not null,
  is_workday   boolean not null,     -- false = свято, true = робоча субота
  note         text,
  primary key (workspace_id, day)
);
```

**Платний креатив** — на самій дизайн-задачі (metadata в `activity_log`, як решта
полів задачі): `design_creative_paid: boolean`, `design_creative_project_cost: number`.
Виставляє менеджер у задачі типу «Креатив». Вартість проєкту — бізнес-інформація,
менеджер її і так знає; **відсоток і ставки лишаються тільки в закритих таблицях**.

## 4. RLS (за [SECURITY.md](SECURITY.md), дені-бай-дефолт)

- `employee_pay_rates`, `employee_pay_month_close`:
  - `SELECT`: `tosho.is_workspace_admin(workspace_id) OR tosho.is_workspace_owner(workspace_id) OR user_id = auth.uid()`
  - `INSERT/UPDATE/DELETE`: тільки admin/owner. Дизайнер свої ставки не пише.
  - **Жодної** політики «team member» — менеджер не читає нічого.
- `employee_pay_defaults`: `SELECT` — admin/owner **або** той, хто сам має рядок
  у `employee_pay_rates` (учасник pay-системи бачить правила гри); запис — admin/owner.
- `ua_workday_exceptions`: читають члени команди (несекретне), пише admin/owner.
- Перед мерджем — прогін чеклиста SECURITY.md «simulate the role»: менеджером
  переконатися, що `select` повертає 0 рядків.

## 5. Розрахунок (клієнтська lib `src/lib/designerPayroll.ts`)

Все рахується **live з наявних подій** — нових записів під час місяця немає,
тому відкоти статусів самі прибирають нарахування:

- робочі дні: пн–пт мінус `ua_workday_exceptions(is_workday=false)` плюс робочі
  суботи. `countWorkdays` викликається **двічі**: без `absences` — для бази,
  з `absences` (`tosho.team_absences`) — для норми;
- роботи: `design_output_upload` за місяць по `user_id`, розкладені на візуали
  (`metadata->>output_kind = 'visualization'`) і макети (все інше); одиниця —
  `(entity_id + назва файлу без розширення)`, дублі схлопуються через Set;
- креативи: задачі `design_task_type='creative'` + `design_creative_paid` +
  поточний статус `approved`, виконавець = дизайнер; сума = cost × percent;
- прогноз: повна база + (темп за нормо-днями × нормо-дні місяця − повна норма,
  якщо >0) × тариф, окремо по візуалах і макетах + платні креативи в
  `pm_review`/`client_review` (очікують затвердження);
- час без таймера (перехідний період): оцінка за **власним темпом** дизайнера
  (його ⌀ час типу з таймерних задач; fallback — норма 15/30 хв), скрізь із
  позначкою «оцінка, таймер не вівся». З наступного місяця — правило: без
  таймера робота не рахується в час (лічильники аномалій уже на дашборді).

## 6. UI

### 6.1 Віджет у хедері (дизайнер) — макет затверджується

Живе **поруч із таймер-віджетом** (`DesignerHeaderTimerWidget` в AppLayout);
рендериться лише коли у користувача є чинний рядок `employee_pay_rates`.

- Пігулка: кільце прогресу (зароблено/прогноз) + «31 304 ₴ · ≈ 44 900» + око.
- **Око** маскує всі суми (`•••••`), стан у localStorage; **дефолт — приховано**
  (вирішено CEO 2026-07-26).
- **Маскування не змінює ширину віджета** (вимога CEO): реальна сума завжди
  відрендерена і резервує місце (ghost-sizer: `visibility:hidden` у masked-стані),
  крапки — окремий шар поверх, відцентровані. Хедер не «стрибає» при перемиканні.
  Без `overflow:hidden` на inline-block — воно зсуває baseline.
- Клік — поповер (стиль валютного віджета, ~330px): hero-сума + прогноз;
  секції База (сітка днів), **Візуали** і **Макети** окремо (зроблено з норми
  на сьогодні, «норма N/день», понад норму × тариф), Креативи (список,
  «чекає затвердження»), минулі 3 місяці (з `month_close`, Фаза 3);
  плашка «до податків».
- Макет: https://claude.ai/code/artifact/7f24fd46-7ced-4d92-a8b1-c7c73436ea0c

### 6.2 Налаштування (SEO/owner)

- Дефолти команди — Налаштування компанії.
- Картка дизайнера в «Команді»: базова ставка + overrides; зміни з 1 числа
  наступного місяця; історія — рядки `employee_pay_rates`.

### 6.3 Задача «Креатив» (менеджер)

Перемикач «Безкоштовний/Платний» + вартість проєкту (валідація ≥ min_creative_cost);
прев'ю «Дизайнер отримає N грн після затвердження».

### 6.4 Адмін «Виплати дизайнерам» (SEO/owner)

Вбудовується в **Фінанси → «Виплати команді»** (там уже живе payroll) окремим
блоком/вкладкою: дизайнери × зароблено × прогноз × перевиконання норми;
кнопка **«Закрити місяць»** (snapshot у `month_close`); експорт Excel.

## 7. Захист від накрутки

- Правило в брифі: «1 візуал = унікальний дизайн» (соціальна угода).
- Red-flag у адмінці: ⌀ час на візуал < 5 хв → позначка «можлива накрутка».
- **Знахідка з даних:** макети часто заливаються у 2 форматах
  (`.ai`+`.pdf` = 1.37–1.68 файла на одну роботу), візуали — майже 1:1 (1.06–1.09).
  Базова назва в обох форматах однакова, тож підрахунок «за унікальну роботу»
  це схлопує сам — на відміну від підрахунку «за файл».
- ⚠️ **Нове після переходу на 200 ₴/макет:** макет коштує вдвічі більше за
  візуал при вдвічі нижчій нормі, тож 70% доплати заробляється на макетах.
  Якщо різниця в трудомісткості цього не виправдовує — з'являється мотивація
  зміщувати роботу в бік макетів. Слідкувати за співвідношенням
  візуали/макети по місяцях у Фазі 3.

## 9. Рішення й що лишилось відкритим (станом на 2026-07-26)

**Ухвалено:**

1. **Файл чи «робота»?** — **унікальна робота** `(задача + базова назва без
   розширення)`. Перезаливи після правок дають 5–9 «файлів» на один візуал.
   *Залишковий ризик:* перезалив під зміненою назвою (`візуал-01_v2.png`)
   порахується як нова робота. Автовідсіву немає — тільки red-flag «⌀ час на
   візуал < 5 хв» (§7) і соціальна угода.
2. **Норма — денна: 7 візуалів + 4 макети.** Тарифи 100 ₴/візуал і 200 ₴/макет.
   Симуляція в §1. Попередні варіанти й чому відпали: місячна 250 з макетами
   поза заліком → нуль завжди; денна 10/5 → 1 200 ₴ на двох за 4 місяці
   (10 візуалів/день вище за історичний максимум 8.3).
3. **Макети рахуються** — окремою нормою й окремим тарифом (розворот
   попереднього рішення «не рахуються»).
4. **Відсутності зменшують норму, але не базу.**
5. **Свята** — стартуємо з **порожнім календарем** винятків (воєнний стан —
   держсвята не вихідні).
6. **Дефолт маскування** — **приховано**; перемикання оком не змінює ширину
   віджета (ghost-sizer, див. §6.1).

**Відкрито:**

1. **Норма командна чи індивідуальна.** Виробіток дизайнерок розходиться вдвічі
   в окремі місяці (квітень: 223 роботи проти 107). Поля override у ставці є,
   рішення не ухвалене.
2. **Співвідношення 100/200 ₴.** Чи справді макет удвічі трудомісткіший —
   від цього залежить, чи не зміститься робота в бік макетів (§7).
3. **Процес по платних креативах.** Механіка є, але жодна з 25 задач не
   позначена — потрібна домовленість, хто і коли ставить перемикач.
4. **Хто ще в системі.** Ставка заведена лише Лєні; Мар'яні — ні, тож віджет
   у неї не показується і доплата не рахується.
