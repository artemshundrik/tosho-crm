# Підказка адрес скрізь + розділення отримувача (Фаза 1)

**Дата:** 2026-07-29
**Статус:** затверджено, план реалізації не написаний
**Фаза 2 (поза цим спеком):** автозаповнення реквізитів за кодом ЄДРПОУ

## Проблема

Адреси в CRM вбивають руками в десятку різних полів. Наслідки: одна вулиця пишеться
трьома способами («вул. Хрещатик» / «Хрещатик вул.» / «вулиця Хрещатик»), у договір
потрапляють опечатки, а менеджер, який не знає адреси Замовника, не має жодної опори.

Окремо — контакт отримувача в логістиці прорахунку зберігається одним полем «Отримувач»,
хоча Нова Пошта приймає ім'я та прізвище роздільно. Місток між ними — здогадка (див.
розділ «Розділення отримувача»), і вона мовчки потрапляє в реальну накладну.

## Рішення

Підказка адрес на довіднику **Нової Пошти** — інтеграція вже стоїть, ключ оплачений.
Юридична адреса лишається **одним текстовим полем** (варіант «А»): жодних міграцій БД,
договори та специфікації працюють без змін.

## Що вже є в коді

Це не нова інтеграція, а дотягування наявної.

- Серверний проксі [`netlify/functions/nova-poshta.ts`](../../../netlify/functions/nova-poshta.ts)
  вже має `Address.searchSettlementStreets` і `Address.getSettlementAreas` у білому списку
  дозволених методів (рядок 19). Автентифікація і воркспейс-гейт на місці. **Нової серверної
  поверхні не з'являється.**
- [`src/lib/novaPoshtaApi.ts`](../../../src/lib/novaPoshtaApi.ts) має `searchNpSettlements`
  (рядок 61) і `listNpWarehouses` (89). Клієнтської функції для вулиць немає.
- [`NovaPoshtaControls.tsx`](../../../src/components/customers/NovaPoshtaControls.tsx) має
  `NpCityCombobox` (71) і `NpWarehouseCombobox` (167) — готовий зразок.

### Обмеження API, що визначає UX

`Address.searchSettlementStreets` приймає `SettlementRef` і шукає вулиці **лише всередині
одного населеного пункту**. Глобального пошуку вулиці не існує, тому будь-яке поле адреси
двокрокове: спершу місто, потім вулиця.

Потрібен саме `SettlementRef` (це `Ref` із `searchSettlements`), а не `CityRef` — логістика
й точки доставки зараз зберігають тільки `npCityRef`, тобто інший ідентифікатор.

## Архітектура: три шари

**1. `searchNpStreets(settlementRef, query, limit)`** у `src/lib/novaPoshtaApi.ts`.
Викликає `callNovaPoshta("Address", "searchSettlementStreets", { SettlementRef, StreetName, Limit })`.
Повертає `NpStreet { ref, present }`, де `present` — готове «вул. Хрещатик».
Порожній результат за `settlementRef === ""` або `query.trim().length < 2` — так само, як
у `searchNpSettlements`.

⚠️ Форму відповіді НП звірити на першому живому виклику — у файлі вже стоїть таке
попередження для решти методів, для вулиць воно так само чинне.

**2. `NpStreetCombobox`** — у тому ж `NovaPoshtaControls.tsx`, дзеркало `NpWarehouseCombobox`.
Пропси: `{ settlementRef, value, onValueChange, onSelect, placeholder?, className? }`.
Свідомо той самий саморобний випадайко, **не Radix Popover** — коментар у файлі (рядки 24-30)
пояснює, що Radix-тригер на полі вводу перехоплював фокус і поле ставало неможливо друкувати.
Затримка 300 мс, як у сусідів.

**3. `AddressAutocomplete`** — новий компонент для полів, де адреса це один рядок.
Веде обидва кроки сам:

- активним вважається текст **після останньої коми**;
- поки місто не обране — підказує міста; на вибір підставляє `settlement.present` + «, »
  і запам'ятовує `settlementRef`;
- після цього підказує вулиці цього міста; на вибір дописує `street.present` + «, »;
- решту (будинок, офіс) користувач дописує руками;
- якщо текст перестав починатися з обраного міста — стан скидається назад у режим міста.

Поле лишається звичайним текстовим весь час: підказки тільки додають, ніколи не блокують
набір. Рендериться як `Input` або як `AutoTextarea` (юридичній адресі потрібне друге).

## Модель даних

**SQL-міграції немає.** Усе, що змінюється, лежить у jsonb.

- `QuoteDeliveryDetails` (`QuoteDeliveryFields.tsx:26-39`) отримує `npSettlementRef?: string`.
- `CustomerDeliveryPoint` (`customerDeliveryPoints.ts:24-47`) отримує `npSettlementRef` +
  серіалізацію `np_settlement_ref` (`:182`, `:185-188`).
- Юридична адреса не змінюється: `customers.legal_entities[].legal_address`,
  `leads.legal_address`, снапшот `orders.customer_legal_address` лишаються текстом.

**Заразом усуваємо розбіжність:** у `src/features/quotes/quotes-page/config.ts:125-141` живе
друга копія типу деталей доставки (`DeliveryDetailsForm`), якій бракує `npCityRef`,
`npWarehouseRef`, `contactName`, `contactPhone` і `deliveryPointId`. Ми все одно правимо цей
тип — лишати дві розбіжні копії безглуздо.

## Розділення отримувача

### Проблема

Роздільні поля вже є у двох місцях із трьох:

- картка клієнта, вкладка Логістика — `DeliveryPointsSection.tsx:215-231`;
- діалог ТТН — `NovaPoshtaTtnDialog.tsx:440-457`.

Одне злите поле «Отримувач» лишилось у `QuoteDeliveryFields.tsx:311-319` — і саме воно
тягнеться в усі чотири діалоги прорахунку та замовлення.

Місток — `splitContactName` (`customerDeliveryPoints.ts:105-109`): бере **перше слово як
ім'я**, весь залишок як прізвище. Для поширеного українського запису «Шундрик Артем» це дає
ім'я «Шундрик» і прізвище «Артем», тобто навпаки. Значення йде через `saveNpRecipient`
(`novaPoshtaApi.ts:198`) прямо в `Counterparty.save` / `ContactPerson.save`, тобто в реальну
накладну.

Спрацьовує при увімкненій галочці «Зберегти адресу в картку клієнта»
(`QuoteDeliveryFields.tsx:327`) у трьох місцях: `NewQuoteDialog.tsx:1516`,
`QuoteBatchBuilderDialog.tsx:1514`, `OrderDeliveryDialog.tsx:198`.

### Рішення

Замінюємо одне поле на два — **«Ім'я», потім «Прізвище»**, з плейсхолдерами «Іван» / «Петренко».
Порядок і підписи навмисно однакові з наявними формами картки та ТТН; неоднозначність усуває
підпис поля, а не порядок.

- `QuoteDeliveryDetails` отримує `contactFirstName` і `contactLastName`.
- `contactName` лишається **похідним** значенням (склейка через `joinContactName`), щоб уже
  збережені прорахунки й замовлення читались без втрат — рівно за зразком, за яким це вже
  зроблено для точок доставки (`customerDeliveryPoints.ts:137`).
- Три виклики `splitContactName` зникають: передаємо справжні поля.
- Сам хелпер лишається **тільки** для розбору старих записів під час читання
  (`customerDeliveryPoints.ts:119-126`), де іншого джерела немає і здогадка виправдана.

По батькові не додаємо: `saveNpRecipient` шле в НП лише `FirstName` і `LastName`, тож третє
поле нікуди б не їхало.

### Дві дрібниці на тому ж рядку

1. Точка доставки зберігається **без `recipientType` і `recipientEdrpou`**, хоча ці поля в неї
   є і діалог ТТН їх читає (`NovaPoshtaTtnDialog.tsx:154-155`), щоразу відкочуючись на дефолт.
   Для вантажу на організацію менеджер вбиває ЄДРПОУ вручну при кожній накладній. Заповнюємо.
2. `npSettlementRef` теж треба класти в точку при збереженні, інакше збережені через галочку
   адреси не зможуть підказувати вулиці.

Обидві — той самий блок коду в тих самих трьох файлах.

## Деградація і помилки

- **Немає ключа НП** → `NovaPoshtaNotConfiguredError` → звичайне поле вводу. Так уже роблять
  місто й відділення (`NovaPoshtaControls.tsx:103-112`, `:207-216`).
- **Помилка мережі / порожня відповідь** → випадайко не показується, набір працює.
- **Місто не обране** → поле вулиці працює як звичайний текст із підказкою обрати місто.
- **Старі збережені точки** не мають `npSettlementRef`, тому підказка вулиць там мовчить, доки
  місто не переоберуть. Це навмисно: тихо перезапитувати ref для кожного старого запису
  означало б лупити по API без потреби.

## Верифікація

- `npx tsc --noEmit`, `npm run lint`, `npm run build`.
- **Живу перевірку не можна зробити на `npm run dev`**: ключ НП живе в серверній функції, а під
  vite на 5173 маршрутів `/.netlify/functions/*` не існує. Потрібен `npx netlify dev` на 8888.
- На першому живому виклику звірити реальну форму відповіді НП для вулиць.
- Сценарій наскрізь: прорахунок → логістика → кур'єр НП → місто → вулиця → «Зберегти адресу
  в картку клієнта» → відкрити картку Замовника й переконатися, що ім'я та прізвище лягли
  в правильні поля, а не навпаки.

## Ризики

- **Форма відповіді НП для вулиць не звірена** — найбільша невідома; парсинг зосереджений в
  одній функції, тож правка буде в одному місці.
- **`AddressAutocomplete` розбирає текст за комами** — це евристика. Вона не може зіпсувати
  дані (поле лишається вільним текстом), у найгіршому разі підказка не з'явиться.
- **Радіус змін** — `QuoteDeliveryFields` спільний для чотирьох діалогів; регресія тут зачепить
  усі. Компенсується тим, що зміни адитивні, а `contactName` лишається похідним.
