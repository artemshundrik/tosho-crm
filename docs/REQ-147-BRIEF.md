# REQ-147 — тестовий акаунт для перевірки CRM у браузері

Бриф для нової сесії. Картка вже в статусі «В роботі».

## Навіщо

Зараз перевірка очима йде або під живою сесією Артема в Browser-панелі (вона
іноді відходить, і тоді дивитись нічим), або ніяк. Playwright у проєкті
налаштований повністю, але без облікового запису не стартує. Через це знімки
живих сторінок доводиться підміняти знімками окремих компонентів — так було
11.09.2026 на REQ-267#p1.

## Що вже готове — НЕ переробляти

Уся обв'язка написана й працює, бракує тільки самого акаунта:

- [`e2e/globalSetup.ts`](../e2e/globalSetup.ts) — два шляхи входу. Шлях 1 саме
  під цю картку: `E2E_EMAIL` + `E2E_PASSWORD` з оточення, тихий вхід через
  справжню форму застосунку. Шлях 2 (`npm run e2e:login`, ручний вхід) лишається
  для випадку, коли треба подивитись під живою людиною.
- [`e2e/writeGuard.ts`](../e2e/writeGuard.ts) — `page.route` глушить усі записи
  на рівні браузера. Supabase у проєкті ОДИН і продівський, тож це головна
  умова, за якої перевірки взагалі можна ганяти. Підміна `window.fetch` НЕ
  працює: supabase-js тримає власне посилання на fetch (перевірено 24.08.2026,
  «заблокований» запит змінив статус прорахунку в проді).
- [`e2e/env.ts`](../e2e/env.ts) — читач `.env.local`, змінна з оточення сильніша
  за файл (у CI значення приходять із секретів GitHub).
- `.auth/` і `.env.local` під `.gitignore`. **Репо публічне** — пароль не має
  потрапити ні в код, ні в доки, ні у відповідь у терміналі.

## Що треба зробити

1. **Створити обліковий запис** у Supabase Auth. Через psql це погана ідея —
   хешування пароля в `auth.users` робиться не руками; потрібен або кабінет
   Supabase, або admin API зі service-role ключем.
2. **Видати доступи** — рядки в `tosho.memberships` (workspace_id, access_role,
   job_role), `tosho.team_members` (team_id), `tosho.team_member_profiles`
   (ім'я). Звірити з `docs/DB_MAP.md`: `workspace_id ≠ team_id`, доступ до
   модулів персональний, у базі лежать ВИНЯТКИ з дефолтів посади.
3. **Прописати `E2E_EMAIL` / `E2E_PASSWORD`** у `.env.local` і в секрети GitHub
   для CI.
4. **Прогнати `npm run e2e`** і переконатись, що набір заходить і бачить дані.
5. **Дописати в `docs/CODEX_WORKFLOWS.md`**, що перевірка очима тепер робиться
   під тестовим акаунтом, а не під сесією Артема.

## Рішення Артема 11.09.2026 — не перепитувати

- **Посада — СЕО / власник.** Щоб на знімках рендерились усі сторінки, зокрема
  фінанси. Це свідомий вибір ширшого доступу заради повноти перевірки.
- **Запис ріжемо тільки `writeGuard`-ом у Playwright**, у RLS нічого не міняємо:
  умова на запис у політиках усіх таблиць — дорого й ризиковано заради тестів.

**Наслідок, який треба тримати на видноті:** акаунт із правами власника в проді
захищений від записів лише тоді, коли ним керує Playwright. Поза набором це
звичайний повноправний обліковий запис. Звідси два практичні наслідки:
пароль має бути довгим і жити тільки в `.env.local` та секретах GitHub, а
`writeGuard` не можна «тимчасово вимкнути, щоб перевірити запис» — для записів
є окрема сесія під живою людиною.

## Питання, яке лишилось відкритим

- **Чи має акаунт бути видимим у списках команди?** Живий рядок «Тестовий
  акаунт» у «Команді», у виборі виконавця дизайн-задачі й у звітах — це шум для
  людей. Варіанти: окремий `employment_status`, фільтр за ознакою, або
  змиритись. Спитати Артема, коли дійде до кроку 2.

## Чого НЕ робити

- Не класти пароль у `.env.local` через мене й не друкувати його у відповіді —
  його вводить і зберігає Артем сам.
- Не чіпати `writeGuard` і `globalSetup`: вони не зламані, їм бракує входу.
