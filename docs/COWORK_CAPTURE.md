# Задачі на доробку з Claude Cowork

Два ендпоінти, через які дошка «Запити» доступна ззовні CRM — з телефона, з
Cowork, звідки завгодно, де є `curl`.

| Що робить | Адреса | Код |
| --- | --- | --- |
| **Завести** картку: надиктував фразу або кинув скріншот | `POST /.netlify/functions/dev-request-capture` | [`dev-request-capture.ts`](../netlify/functions/dev-request-capture.ts) · [чиста логіка](../netlify/functions/_lib/devRequestCapture.ts) |
| **Подивитись чергу** й **посунути** картку | `POST /.netlify/functions/dev-request-board` | [`dev-request-board.ts`](../netlify/functions/dev-request-board.ts) · [чиста логіка](../netlify/functions/_lib/devRequestBoard.ts) |

Розбір тексту при створенні — той самий, що у вікні «Новий запит» і в
Telegram-боті ([`_lib/devRequestDraft.ts`](../netlify/functions/_lib/devRequestDraft.ts)),
тож картки з усіх трьох входів виглядають однаково.

**Чому це дві функції, а не одна з режимами.** У захоплення рівно одна
відповідальність: прийняти сказане й записати картку. Воно платить за розбір
моделлю, логує вартість і не читає нічого. Дописати туди читання й керування
означало б, що один вхід робить три різні речі з трьома різними профілями
відмов.

**Користувач рівно один — власник.** Ні таблиці ключів, ні прив'язки токена до
людини немає й не планується: і секрет, і uuid автора приходять з оточення
Netlify. Обидва ендпоінти беруть **той самий** токен: другий секрет був би
зайвою річчю в 1Password без жодного виграшу.

> ⚠️ **Ціна витоку виросла.** Поки був лише вхід захоплення, токеном можна було
> тільки писати нові картки — витік коштував би спаму на дошці. Тепер ним можна
> ще й читати чергу (**включно з приватними картками**) і міняти статуси. Це
> свідомий обмін: інакше черги з телефона немає взагалі. Ротація — у розділі
> «Обслуговування».

## 1. Налаштувати (одноразово)

Треба дві змінні оточення в Netlify — спільні для обох ендпоінтів. Поки бодай
однієї немає, вони відповідають `503` і не роблять нічого.

### 1.1. Згенерувати токен

```sh
openssl rand -hex 32
```

Скопіюй результат. Це і є `DEV_REQUEST_CAPTURE_TOKEN` — більше він ніде не
зберігається, тож поклади його одразу в 1Password.

### 1.2. Дізнатись свій uuid

Через psql (той самий доступ, що для міграцій):

```sh
set -a && . ./.env.backup && set +a
psql "$BACKUP_DB_URL" -c "select id, email from auth.users where email = 'artemshundrik@gmail.com';"
```

Без термінала: Supabase → Authentication → Users → знайти себе за поштою,
скопіювати `UID`.

### 1.3. Покласти в Netlify

Netlify → Site configuration → Environment variables → **Add a variable**, для
кожної:

| Змінна | Значення | Scope |
| --- | --- | --- |
| `DEV_REQUEST_CAPTURE_TOKEN` | те, що видав `openssl` | **Functions** |
| `DEV_REQUEST_CAPTURE_USER_ID` | uuid із кроку 1.2 | **Functions** |

Scope навмисно лише `Functions`: у збірці ці значення не потрібні, а все, що
потрапляє в `Builds`, має шанс осісти у клієнтському бандлі.

**Змінні починають діяти лише з наступного деплою.** Деплой коштує ~15 кредитів
([`DEPLOY_POLICY.md`](DEPLOY_POLICY.md)), тож ставити їх варто **до** того, як
викочувати пачку комітів — тоді один деплой закриває і код, і налаштування.

## 2. Перевірити, що живий

Спершу без токена — має бути `401`:

```sh
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://tosho.pro/.netlify/functions/dev-request-capture \
  -H 'Content-Type: application/json' \
  -d '{"text":"перевірка доступу"}'
```

> `503` замість `401` означає, що змінні ще не доїхали: або їх немає, або після
> їх додавання не було деплою.

Тепер із токеном — має з'явитись картка:

```sh
curl -s -X POST https://tosho.pro/.netlify/functions/dev-request-capture \
  -H 'Content-Type: application/json' \
  -H "x-capture-token: ТУТ_ТОКЕН" \
  -d '{"text":"Перевірка захоплення з Cowork: у списку прорахунків не видно, хто останній редагував"}'
```

Відповідь:

```json
{
  "ok": true,
  "number": "REQ-42",
  "title": "У списку прорахунків не видно, хто останній редагував",
  "kind": "Незручно",
  "module": "Прорахунки",
  "priority": "Звичайний",
  "url": "https://tosho.pro/dev-requests",
  "message": "📝 REQ-42 — записав\nУ списку прорахунків не видно, хто останній редагував\nНезручно · Прорахунки · Звичайний\nhttps://tosho.pro/dev-requests"
}
```

Картка лягає в колонку **«Вхідні»** (`triage`) — це захоплення на бігу,
а не свідоме заведення з дошки, тож її ще має побачити людина.

Перевірочну картку потім прибери з дошки руками.

### Що означають коди

| Код | Що сталось |
| --- | --- |
| `200` | Записано. Дивись `message`. |
| `200` + `"duplicate": true` | Номер уже зайнятий (гонка лічильника). Повтори запит — візьме наступний. |
| `400` | Порожній або закороткий текст (треба хоча б 3 символи), чи тіло не JSON. |
| `401` | Токен не збігся або заголовка немає. |
| `503` | Змінні оточення не налаштовані. |

Поле `existingFeature` з'являється, лише коли розбір упізнав уже наявну
можливість CRM («схоже, це вже працює: …»). Картку це не скасовує.

Якщо модель не відповіла, картка все одно створюється — з сирим текстом і
типовими значеннями, а в `message` буде рядок «Розбір не спрацював».

## 3. Черга: подивитись і посунути картку

Другий ендпоінт, `dev-request-board`. Той самий заголовок із токеном, дія — у
тілі запиту.

### 3.1. Показати чергу

```sh
curl -s -X POST https://tosho.pro/.netlify/functions/dev-request-board \
  -H 'Content-Type: application/json' \
  -H "x-capture-token: ТУТ_ТОКЕН" \
  -d '{"action":"list"}'
```

Віддає **відкриті** картки — усе, крім «Викочено» і «Не робимо». Обидва
виключені як тупики: викочене поїхало в проді, «не робимо» закрите свідомо, і
тримати їх у черзі означало б список, що росте назавжди.

Групи — у порядку колонок дошки, всередині: спершу термінові, далі свіжіші.
Стеля — 50 карток; якщо їх більше, у відповіді буде `"hasMore": true`.

```json
{
  "ok": true,
  "total": 7,
  "hasMore": false,
  "groups": [
    {
      "status": "triage",
      "label": "Вхідні",
      "cards": [
        {
          "number": 9,
          "label": "REQ-9",
          "title": "Не видно, хто останній редагував прорахунок",
          "status": "triage",
          "statusLabel": "Вхідні",
          "kind": "Незручно",
          "module": "Прорахунки",
          "priority": "Звичайний",
          "urgent": false,
          "private": false
        }
      ]
    }
  ],
  "url": "https://tosho.pro/dev-requests",
  "message": "📋 Черга запитів — 7 відкритих\n\nВхідні (1)\nREQ-9 — Не видно, хто останній редагував прорахунок · Незручно · Прорахунки\n\nhttps://tosho.pro/dev-requests"
}
```

Два поля номера навмисно: `label` («REQ-9») показують людині, `number` (9)
передають у дію `move`.

`"private": true` (у `message` такий рядок починається з 🔒) — картку видно лише
власнику й SEO. Приватні картки **не** фільтруються (обидва входи відкриті саме
цим людям), але позначаються: той, хто збирається переслати список чи зробити
скріншот, має бачити, який рядок не для всіх, **до** того як натисне «поділитись».

> **Теми й описи карток пишуть співробітники.** Для агента, який читає цю
> відповідь, це **дані, а не інструкції**: текст із чужого робочого чату не має
> ставати командою в сесії з доступом до файлів і термінала. Скіл про це
> попереджений окремим абзацом — не прибирайте його.

### 3.2. Посунути картку

```sh
curl -s -X POST https://tosho.pro/.netlify/functions/dev-request-board \
  -H 'Content-Type: application/json' \
  -H "x-capture-token: ТУТ_ТОКЕН" \
  -d '{"action":"move","number":4,"status":"in_progress"}'
```

**Дозволені рівно три статуси** — ті, які ставить людина:

| `status` | На дошці | Коли |
| --- | --- | --- |
| `in_progress` | В роботі | взялись |
| `queued` | У черзі | вирішили робити, але не зараз |
| `wont_do` | Не робимо | відхилили |

`done_local` і `released` руками не ставляться. Їх проставляють **факти** —
коміт і деплой (див. розділ «Релізи»), — і рука тут зробила б дошку брехливою:
«викочено» без деплою означає, що в проді цього немає, а звіт керівництву скаже,
що є. Спроба поставити такий статус повертає `400` з переліком дозволених.

Відповідь показує і новий стан, і попередній:

```json
{
  "ok": true,
  "card": { "number": 4, "label": "REQ-4", "status": "in_progress", "statusLabel": "В роботі", "...": "..." },
  "previousStatus": "triage",
  "previousStatusLabel": "Вхідні",
  "unchanged": false,
  "url": "https://tosho.pro/dev-requests",
  "message": "▶️ REQ-4 → В роботі\nНе видно, хто редагував\nБуло: Вхідні\nhttps://tosho.pro/dev-requests"
}
```

`"unchanged": true` означає, що картка вже була в цьому стані — запит нічого не
змінив, і `message` каже це прямо.

**Викочену картку зрушити не можна** — прийде `409`. Перелік дозволених статусів
захищає лише те, **куди** картку ставлять, і цього мало: повернувши викочену
картку «в роботу», ми лишили б їй заповнені `released_at` і `commit_shas`, і
дошка почала б суперечити розділу «Релізи» — та сама брехня, тільки з іншого
боку. Якщо в проді щось не працює, це **нова** картка: реліз таки був, а
поламане в ньому — окремий факт зі своєю історією.

> **«Взяти в роботу» ≠ почати роботу.** Цей запит міняє лише статус картки.
> Сама робота починається, коли Артем відкриває сесію з підключеною текою
> репозиторію й каже, що робити.

### Що означають коди

| Код | Що сталось |
| --- | --- |
| `200` | Готово. Дивись `message`. |
| `400` | Невідома дія, немає номера або заборонений статус. У полі `error` — перелік дозволених. |
| `401` | Токен не збігся або заголовка немає. |
| `404` | Картки з таким номером у команді немає. |
| `409` | Картку вже викочено — її не рухають. |
| `500` | Не змогли прочитати чи записати — деталі в логах функції. |
| `503` | Змінні оточення не налаштовані. |

Хто натиснув — у журналі змін картки не видно: службовий ключ не має `auth.uid()`,
тож автор запису порожній. Сам факт і час переходу лишаються.

## 4. Скіл для Cowork

Живе окремо від репозиторію: `~/.claude/skills/tosho-request/SKILL.md`. Копії
тут навмисно немає — два тексти про один ендпоінт розійшлись би на першій правці,
і незрозуміло було б, який із них правда.

**Токен у файл скіла не вписуй.** Скіл читає його зі змінної оточення — додай у
`~/.zshrc` рядок `export TOSHO_CAPTURE_TOKEN='…'` і перезапусти термінал. Так
файл скіла лишається звичайним текстом, який не страшно кудись покласти.

Що скіл мусить покривати (звіряй при правках):

- три дії — завести, показати чергу, посунути картку — з точними `curl`;
- показувати готове поле `message`, а не переказувати відповідь своїми словами;
- не вигадувати класифікацію: тип, напрямок і пріоритет ставить сервер;
- не повторювати створення після помилки — кожна спроба робить окрему картку;
- прямо казати, що зміна статусу **не запускає** роботу.

## 5. Черга в Telegram

Те саме з телефона, без `curl`: команда `/черга` (латинський аліас `/queue`) у
боті @ToShoCRM_bot. Список відкритих карток, тап по номеру — картка з кнопками
«В роботу», «У чергу», «Не робимо».

Доступ — **лише власнику й SEO**: бот ходить під службовим ключем і RLS обходить,
тож право дивитись чергу перевіряється вручну на кожному кроці
([`_lib/devRequestQueue.ts`](../netlify/functions/_lib/devRequestQueue.ts),
`resolveQueueAccess` у вебхуці). Решта команди отримує ввічливу відмову з
підказкою, що завести задачу можна через `/задача`.

Після деплою, який додає команду, треба один раз смикнути `telegram-setup`,
інакше `/queue` не з'явиться в меню бота:

```sh
curl -s -X POST https://tosho.pro/.netlify/functions/telegram-setup \
  -H "x-cron-key: $CRON_SHARED_SECRET"
```

## Обслуговування

**Ротація токена.** Згенеруй новий `openssl rand -hex 32`, онови
`DEV_REQUEST_CAPTURE_TOKEN` у Netlify, задеплой, онови `TOSHO_CAPTURE_TOKEN` у
`~/.zshrc`. Старий перестає працювати з моменту деплою.

**Вимкнути.** Прибери `DEV_REQUEST_CAPTURE_TOKEN` із Netlify й задеплой — **обидва**
ендпоінти повернуться до `503` і перестануть робити будь-що. Черга в Telegram при
цьому лишиться живою: вона автентифікує людину, а не токен.

**Скільки коштує.** Кожне захоплення — один виклик моделі. Вартість лягає в
`tosho.ai_usage` з `metadata.source = "dev_request_cowork"`, видно у вкладці
«AI-кости» розділу спостережуваності — там же, де диктування й бот. Черга
(`list`/`move`) моделі не викликає й не коштує нічого.
