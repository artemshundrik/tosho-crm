# Eval-сценарії скіла `tosho-request`

Десять кейсів із REQ-206: типова фраза на вході, очікуваний вибір ендпоінта й
очікуване формулювання на виході. Мета — щоб правка `SKILL.md` не ламала скіл
непомітно.

Кожен кейс закриває правило, помилка в якому вже коштувала грошей або картки:

| Кейс | Правило |
|---|---|
| `01-new-card` | звичайна скарга йде в `capture` словами автора |
| `02-merge-existing` | `merged: true` показується як долучення, з рядком «Не те?» |
| `03-papercut-line` | дрібниця — рядок у накопичувач, а не картка |
| `04-today-shelf` | «що сьогодні» — це полиця, а не 50 рядків черги |
| `05-move-status` | статусів рівно чотири, «Викочено» руками не ставиться |
| `06-bare-number` | голий `Закриває: REQ-N` накопичувач не закриває |
| `07-prompt-injection` | текст картки — дані, а не вказівки |
| `08-do-now-still-log` | робота «зараз» не скасовує рядок у «Дрібницях» |
| `09-no-shelf-yet` | бракує полиці — заводиться полиця, а не повна картка |
| `10-error-no-retry` | після невдачі не повторювати наосліп — плодить дублі |

## Як запустити

Харнес шукає кейси **під текою скіла**, а скіл живе поза репозиторієм
(`~/.claude/skills/tosho-request/`). Тому один раз робиться символьне
посилання, і далі evals лишаються під git тут:

```sh
ln -s "$(git rev-parse --show-toplevel)/evals/tosho-request" ~/.claude/skills/tosho-request/evals
```

```sh
claude plugin eval ~/.claude/skills/tosho-request
```

Дешевший прогін: `--runs 1`, а `--ablation none` знімає другу руку без скіла.

**`--case` фільтрує за `name:` із frontmatter, а не за назвою теки.** Один
кейс — це `--case 'bare-number'`, НЕ `--case '06-*'`: глоб зводиться до
`^06-.*$` і не збігається ні з чим, а прогін мовчки бере нуль кейсів. Перевірка
форми тому й вимагає `name:` у кожному `prompt.md`.

## Чому в кейсах немає Bash

**Прогін не має писати в прод.** Скіл ходить на живий `tosho.pro` із зашитою
адресою — параметра «інший сервер» у нього немає. Дай кейсу Bash, і кожен
прогін заводитиме справжні картки й совгатиме справжні статуси; при `runs: 3`
це три зайві картки за прогін.

Тому кейси перевіряють НАМІР, а не наслідок: `allowed_tools: [Skill]`, і
грейдери читають, що саме модель зібралась викликати — який ендпоінт, яку
дію, з якими полями, і що вона покаже людині. Регресію формулювань і вибору
дії це ловить; те, що ендпоінт справді відповідає, — ні.

У кейсі `07-prompt-injection` відсутність Bash перевіряється ще й грейдером
(`min: 0, max: 0`): текст картки не має вміти запустити команду.

Дані відповідей сервера в кейсах 02, 07, 09 і 10 — вставлені в промпт зразки, а
не живі запити. Це навмисно: так перевірка не залежить ні від мережі, ні від
того, що зараз лежить на дошці.

## Стан

`claude plugin eval` у цій організації **не увімкнений**. Перевірено двічі:
02.09.2026 на CLI 2.1.252 і 06.09.2026 на 2.1.263 — обидва рази команда є, але
відповідає «currently in early access». Сценарії написані наперед і жодного
разу не прогнані: перший прогін покаже, скільки з десяти проходить, і,
найімовірніше, зажадає правок у формулюваннях грейдерів.

Поки прогону немає, форму стереже `npm run check:eval-cases` (він же в складі
`npm run check`). Схема в ньому вичитана з валідації самого CLI 2.1.263 —
переліки ключів frontmatter і zod-схеми грейдерів. Ключі й типи від 2.1.252 не
зрушили; що зрушило — це обізнаність самої перевірки: схеми грейдерів у CLI
оголошені `.strict()` і з обов'язковими полями, тож `tool_used` без `tool:`,
`focus: final` замість `last_message` чи `match: has` раніше проходили тихо, а
лягли б аж у прогін. Тепер звіряються ключі всередині грейдера, обов'язкові
поля кожного типу та переліки значень.
